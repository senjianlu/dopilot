# Plan 评审:第 03 轮

## 问题清单
- [plan-blocker] R-01 将可被权威终态覆盖的 `lost` 当作不可逆最终结果，会错误累计连续失败并可能误禁用调度。
  - 详情:定位：plan.md:94-96、139-153。既有状态机明确 `lost` 是 soft terminal，后到的 agent `finished/failed/canceled` 可覆盖它并重新 rollup Task；但方案对所有 `TASK_TERMINAL` 写入永久的 `outcome_recorded_at`，并在兜底时封口。若先记录 `lost` 为失败、随后 agent 恢复并上报 `finished`，Task 会变成功而连续错误计数和自动禁用结果不会纠正。需在方案中定义对 soft-lost 的最终化策略（例如延后到不可再覆盖的确认点，或引入可逆的结果贡献账本），并新增“记录后 lost 被 finished 覆盖”的自动化用例。
- [major] R-02 结果记录器会因日志定稿先后不同而按错误顺序更新同一 Schedule 的连续错误计数。
  - 详情:定位：plan.md:95、150-153、TC-19~TC-21。方案虽按 `(finished_at, id)` 排序，但对尚在 drain 的较早任务会跳过，再处理同一 Schedule 中已定稿的较晚任务；较早任务之后定稿时才补记，实际计数顺序变为“定稿顺序”而不是运行结果顺序。例如“失败 A（日志未定稿）→ 成功 B（已定稿）”会先将计数清零、后把 A 加为 1，而正确连续结果应为 0。需规定同一 Schedule 只能处理按完成时间排列的连续已定稿前缀（遇到更早未定稿项即阻塞后项），或采用等价的有序提交机制；补充该交错场景测试。
- [major] R-03 通知去重只描述了逻辑规则，未定义可并发兑现的数据库约束或原子写入方式。
  - 详情:定位：plan.md:92-93、160-167、TC-24。事件消费者、日志消费者、StreamGuard 和维护循环可在不同 session 中同时调用 `notify`；仅有 `(read_at, created_at)` 普通索引时，两个事务都可能读不到未读行并各插入一条相同 `dedupe_key`，违反“活跃期唯一、count+1”的方案承诺。需在迁移和服务设计中加入未读 `dedupe_key` 的部分唯一约束，并定义 `INSERT ... ON CONFLICT`/重试等原子 upsert 路径；测试应覆盖两个独立 session 并发上报同一键后只保留一行且计数为 2。

## 总评
测试用例表逐条声明了 A 档与完整原始输出证据形态，C 档为 0，证据契约合规。前两轮已指出的问题已被修订，但结果记录器仍与既有 soft-lost 语义及连续计数时序不自洽，通知去重也缺少并发保障，因此本轮应退回修订方案后重评。
