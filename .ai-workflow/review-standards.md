# 评审标准(评审者手册)

本文件是本项目代码评审的唯一权威标准,由评审指令
(.ai-workflow/prompts/review.md)显式引用。

评审者是本项目的独立代码评审者:只评审,不修改任何代码,也不在工作区
新建或改动任何文件(只读沙箱机器强制,任何写入都会失败);可执行的
动作以下方「评审动作边界」为准。

## 评审输入

- 当前工作区的未提交改动(含新增文件)
- 本轮任务的 plan.md(路径由评审指令给出)

核心问题永远是两个:实现是否忠于 plan?plan 中的测试用例是否真实覆盖并通过?
此外有一个**不计入 pass/fail** 的固定问题——范围核对(见下方同名小节)。

## 评审动作边界

评审在**只读沙箱**中直审原仓库(机制见 docs/decisions/0005),任何写入
都会被沙箱拒绝;评审动作以此为前提:

- **允许**:读取代码与 diff、grep 类检索;运行**确无写入副作用**的
  只读检查(如 `tsc --noEmit`、禁用缓存的 lint)。命令因只读沙箱的
  写失败而报错时,**不视为代码缺陷**,该项转证据核验并在评审输出中
  注明"未能在边界内核验"。
- **不运行任何测试**(含单元测试——多数 runner 需写缓存,只读下天然
  失败;测试核验整体走下方证据协议)。
- **超时与中止**:单条命令设超时上限(默认 5 分钟,建议用 timeout 等
  机制强制),超时即中止并在评审输出中记录"未能在边界内核验",不得
  反复重试拉长评审;疑似不自终止的命令一律不执行。
- **禁止**:安装或更新依赖(npm / pnpm install、pip 等)、构建
  (next build 等)、启动任何服务器或长驻进程(next dev、uvicorn、
  docker 等)、E2E(playwright)、访问网络。只读下多数天然失败,
  保留为行为约束:不得尝试。
- **证据协议**:测试真实性核验一律走证据,**且逐条按 plan.md 声明的证据
  档位执行**,不得对全部用例统一套用最严标准。档位定义、约束与逐档核验
  规则见下方「测试证据档位」小节。

## 测试证据档位(证据契约)

证据形态在 **plan 阶段**即以契约形式定好:plan.md 的测试用例表逐条声明
「档位」与「证据形态」,实现者按契约留证,评审者按契约核验。三档定义:

| 档 | 适用范围 | 证据形态 |
|---|---|---|
| **A** | 可由非交互命令判定的用例(单元测试、E2E runner、lint、tsc、grep/静态校验、脚本) | 由 `.ai-workflow/scripts/evidence.sh` 包住命令产出的 **rawf-evidence v1** 文件(执行命令 + 完整 stdout/stderr + 退出码,落任务目录 `evidence/`);格式完整性由 `evidence-check.sh` 在评审前机器核验(见下方「rawf-evidence v1 格式」) |
| **B** | 靠静态事实即可确证的断言(配置生效、文案键存在、路由已注册) | 日志片段,或代码/文档引用——引用**须带 `文件:行号`**,供评审自行 grep 复核 |
| **C** | 确实无法自动化的人工交互验证(真机视觉、剪贴板、系统弹窗、跨设备) | 实现者陈述 + 关键锚点(相关代码位置、截图文件名、控制台片段) |

档位约束:

- **A 档强制**:凡可自动化者一律 A 档,**不得降档**。plan 中把可自动化项
  写成 C 档 → major。
- **C 档上限**:C 档条目数 ≤ 该 plan 测试用例总数的 1/3(向下取整);
  **总数 < 3 时至多 1 条**。超限 → major。每条 C 档须在 plan 中写明
  **为何不可自动化**,缺理由 → major。
- **形态优先级**:日志/文本证据优先于截图。截图只能作为 C 档的补充锚点,
  **不得作为任一用例的唯一证据**——评审在只读沙箱中无法读取图像。
- **向后兼容**:plan **未声明档位**的用例(本约定之前的历史任务)一律
  **按 A 档处理**。

### rawf-evidence v1 格式(A 档证据的唯一合法形态)

`evidence.sh <TC-id> [-l <label>] -- <命令...>` 写出
`evidence/<TC-id>[-<label>].log`,已存在则拒绝覆盖(重跑另起 label)。
文件结构与完整性定义(evidence-check 的唯一判据,机制与取舍见
docs/decisions/0010):

```
# rawf-evidence v1          ← 第 1 行,逐字
tc: TC-07                   ← 必填
label: r02                  ← 可空
cmd: pytest tests/test_x.py -v   ← 必填非空;argv 逐项 shell 引用,原样可复跑
cwd: /abs/path              ← 必填
git_head: <sha>[ dirty]     ← 必填
started: <ISO 8601>         ← 必填
--- output ---              ← 正文起始标记,独占一行
<stdout 与 stderr 合流,完整,不截断>
--- end ---                 ← 尾部起始标记;正文后先写一个换行再写本行
exit: 0                     ← 必填,0..255 整数
finished: <ISO 8601>        ← 必填
bytes: 1234                 ← 必填 = 正文区字节数
```

正文区 = `--- output ---` 行之后、**最后一个** `--- end ---` 行之前(不含
其前导换行)的全部字节,长度必须等于 `bytes:`;正文本身出现 `--- end ---`
字样不影响判定。**格式问题由机器判定,不是评审意见**:evidence-check 不通过
时 review.sh 直接拒绝启动评审并开出补交清单,不消耗评审轮次。

### 两种留证写法

plan 的「证据形态」列写明用的是哪种,评审据此解读 `exit:`:

- **(a) 直接包住被测命令**:`exit:` 即被测命令退出码,评审拿它对照用例预期
  结果——预期本身可以是非零退出码或报错输出,**非零不等于失败**;
- **(b) 包住断言脚本**:脚本内部执行被测命令并断言输出/退出码,全部断言
  成立才 exit 0;此时 `exit: 0` 表示用例通过,被测命令的退出码在正文里。

### 逐档核验规则

评审前先读 plan.md 测试用例表的「档位」列,**逐条按该列核验**,不得对全部
用例统一套用 A 档要求:

- **A 档**:格式(命令是否记录、输出是否完整、退出码是否存在)**已由
  evidence-check 机器核验**,评审指令中附有逐条结果;评审**不再就格式提
  意见**,只核三件事:① `cmd:` 是否对应该用例的步骤、是否覆盖用例要求的
  场景;② `exit:` 与正文是否符合该用例在 plan 中写明的预期结果(按上方
  「两种留证写法」解读);③ 实现记录中的结果与证据是否一致。判定:证据
  (exit / 正文)与用例预期矛盾却报 pass,或证据与记录矛盾 → **blocker**
  (虚报);`cmd:` 未覆盖用例要求的场景或步骤 → **major**;格式 → 不列。
  评审指令注明"历史任务,未经机器核验"(plan 无 `evidence_format: v1`)
  时,沿用旧规则自行核对:缺失或不完整 → blocker,detail 列明补交清单。
- **B 档**:核验引用的 `文件:行号` 或日志片段——**引用不存在 → blocker**;
  **引用存在但不支持结论 → major**。
- **C 档**:**默认采信**实现记录中的结果描述。仅在下列三种情形判问题:
  1. 描述与 plan 的预期结果或其他证据**自相矛盾**;
  2. 该用例在 plan 中**并非 C 档**(即实现阶段被擅自降档);
  3. **关键锚点缺失**,使描述完全无法定位。

  **不得仅以「无原始命令输出」为由对 C 档判 blocker。**
- **任一档位**:证据与实现记录**矛盾** → 按虚报测试处理(blocker)。
- **机械性更正**:plan 测试表中带 `〔机械性更正:原文「…」;理由:…;见实现记录
  D-NN〕` 标注的条目,**以更正后的文字为验收基准**。评审核验该更正是否只修正
  笔误/排序/转义/算术、未改变用例意图、未删减场景、未放宽断言,并与实现记录
  偏差表中的"替代"条目一致——是 → 按更正后的文字核验;否 → **major**(擅自
  改写用例),detail 给出原文与更正对照。

**阅读建议(不是禁区)**:所有文件都可按需读取;先读证据文件头部与尾部,
有疑点再深入正文,不必通读长日志。evidence-check 报告中的 EXTRA-ROW
(plan 没有的用例)纳入范围核对,不单独判问题。

## 范围核对(不计入 pass/fail)

两级评审各有一个**固定问题**,结论写入输出的 `scope_findings`(字符串数组,
每条含定位与一句说明),渲染为评审文件的「范围核对」节;**不定严重度、不
计入 pass/fail、不重复列进 issues**,由用户裁决(机制见 docs/decisions/0011):

- plan 阶段:方案是否超出「需求原文」?「改动范围」「实现方案」中不是需求
  直接要求的条目,plan 是否说明了"实现必需"的理由;顺手项是否已移入
  「非目标」。plan 缺「需求原文」或「非目标」节 → major(模板硬要求)。
- 实现阶段:diff 中是否存在 plan「改动范围」之外、且实现记录「与方案的
  偏差」表未声明的改动?偏差表中是否有标为「追加」但无用户确认记录的项?

## 严重度定义(唯一权威来源)

- **plan-blocker**:方案/架构层面的错误,修改代码无法解决,必须退回方案阶段
- **blocker**:实现层错误,导致功能不可用、数据损坏或安全漏洞
- **major**:实现层缺陷,功能可用但存在正确性或健壮性问题,必须修复
- **minor**:风格、可读性、边缘优化,可修可不修

## 判定规则

以下规则适用于**实现层评审**(review.sh,对已实现的代码 diff):

- 存在任一 blocker 或 major → **fail**
- 仅有 minor 或无问题 → **pass**
- plan-blocker 单独列出,不计入 pass/fail,但必须置顶显著标注

## plan 阶段评审(plan-review)语义

**plan 阶段评审**(plan-review.sh,实现前审 plan.md)另用一套判定:此时尚无
实现,**不使用 blocker**;判定规则为——

- 存在任一 **plan-blocker 或 major → fail**(须就地修订 plan.md 后重评)
- 仅有 minor 或无问题 → **pass**

即:同一 plan-blocker 严重度,在实现层评审中不计入 pass/fail(单独升级),在
plan 阶段评审中直接计入 fail——因为 plan 阶段的全部目的就是拦截 plan-blocker。
两套规则分域适用,互不覆盖。

### plan 阶段的严重度判据(返工判据)

plan 阶段 major 的唯一判据:**若该问题留到实现阶段才被发现,是否需要推翻已
完成的实现(返工)?** 是 → major(或 plan-blocker);否 → minor。据此:

- **判 minor**:用例中意图明确的机械性错误(笔误、排序、转义、算术、措辞)——
  实现者按「机械性更正」条款就地更正;章节间不影响实现方式的表述不一致;docs
  回写清单的遗漏(实现层评审按 docs 回写规则核对)。
- **仍判 major**:验收标准缺覆盖(含异常/边界路径;只测 happy path 即 major)、
  验收标准不可达或自相矛盾、契约/数据模型/接口错误、证据契约违规、缺「需求
  原文」或「非目标」节。
- 风格、个人偏好、等价写法之争一律不列。

### 分轮模式:第 1、2 轮全量穷尽,第 3 轮起收敛

机制与取舍见 docs/decisions/0012;plan-review.sh 每轮快照 plan.md,并把模式、
上一轮评审文件与两轮快照间的修订 diff 注入评审指令。

- **第 1、2 轮:全量穷尽评审**。逐一走完五个维度(架构与正确性、与既有约定的
  冲突、验收覆盖、证据契约、范围自省),一次列出全部问题(含 minor),不得在
  找到前几条后停止;`overall` 逐维度各写一句检查结论。第 2 轮另需先逐项核验
  上一轮的 plan-blocker/major。
- **第 3 轮起:收敛评审**。① 先逐项核验上一轮的 plan-blocker/major,未解决的
  保留原严重度;② 修订部分(diff 中的改动)按五个维度完整评审;③ 未修订部分的
  新发现**只报 plan-blocker**,其它至多 minor。未修的 minor 不要求逐轮重复列出,
  由实现阶段经 `plan-review.sh __minors` 汇总全部轮次后交接。
- **回退**:第 3 轮起若无上一轮快照(该轮早于快照机制),按全量穷尽评审。
- 评审期间 plan.md 被修改 → 本轮结论作废,不发布、不消耗轮次。
