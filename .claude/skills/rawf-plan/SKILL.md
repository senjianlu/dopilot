# rawf-plan:方案阶段

## 步骤

1. 与用户对齐需求。有歧义先问,不要带着猜测写方案。
2. 创建任务目录 `.ai/<yyyy-mm-dd>/<task-slug>/`(日期用今天,slug 用简短
   kebab-case 英文);若同名目录已存在,询问用户是续做还是换名。同时在其下
   建两个固定子目录并各放 `.gitkeep` 占位(空目录才能随任务入库):
   `evidence/`(证据:测试输出、截图、验证记录)与 `assets/`(资源:Design
   稿、参考图、外部素材)。
3. 将任务目录相对路径(如 `.ai/2026-07-05/add-login`)写入 `.ai/.current-task`。
4. 调研代码库后,复制 `.ai-workflow/templates/plan.md` 到任务目录并填写,
   保持 `status: draft`,frontmatter 保留 `evidence_format: v1`(A 档证据走
   evidence.sh 标准格式与机器核验的标记)。**「需求原文」与「非目标」为
   必填节**:需求原文引用用户原话并写一句话交付物;改动范围里不是需求直接
   要求、但实现必需的条目写明理由;纯顺手项移入非目标。plan 评审会就此
   做范围自省(结论进「范围核对」节,不计入 pass/fail)。
   **写作粒度**:plan 写到能判断方案对错、能验收为止——契约、数据模型、接口、
   验收标准、风险;不预写实现代码与逐行细节。plan 里每一句都是评审面,写得
   越多,可被挑的问题越多。
5. 测试用例章节为硬要求:每条含编号 TC-NN、前置条件、步骤、预期结果,
   且至少一条覆盖异常/边界路径。没有可执行的验收标准的方案不算方案。
   **证据契约同为硬要求**:每条用例须**逐条声明档位与证据形态**(档位
   权威定义见 .ai-workflow/review-standards.md「测试证据档位」)——
   - **可自动化者一律 A 档、不得降档**:凡能由非交互命令判定(测试、
     lint、tsc、grep、脚本)的用例都必须走 A 档;把这类用例写成 C 档
     会在 plan 评审中判 major;
   - **C 档 ≤ 用例总数 1/3 且须写明不可自动化的理由**(总数 < 3 时至多
     1 条);上限是上限不是下限,没有人工交互项时 C 档为 0 才是常态;
   - 证据形态优先取日志/文本;截图不得作为任一用例的唯一证据;
   - A 档的证据形态写明留证写法:(a) `evidence.sh` 直接包住被测命令,或
     (b) 包住断言脚本(exit 0 = 全部断言成立),评审据此解读退出码。
6. 【plan 评审闸,仅当本方案预计触及文件 > 10 时执行(≤ 10 不走此闸),
   在确认闸之前】
   以**后台方式**运行 `bash .ai-workflow/scripts/plan-review.sh`(Claude Code
   中用 `run_in_background`,`timeout` 不低于 4000000 ms),启动后
   **直接结束回合**、不轮询等待,完成通知唤回后再分流。退出码 3 = 执行异常:stderr 含
   "已终止"(看门狗)→ 重跑一次;其它把 stderr 报用户后停下。按结果分流:
   - fail(有 plan-blocker 或 major)→ **就地修订 plan.md**(尽量一次改完),
     重跑评审;脚本强制轮次上限(**默认 5 轮**),达上限(exit 3 提示
     "N 轮上限")仍不收敛 → 停止,把分歧交用户敲定,不自行绕过。
   - 分轮模式(review-standards.md「分轮模式」):第 1、2 轮为全量穷尽评审,
     会一次列出全部问题(含 minor),这两轮的意见尽量一次改完;第 3 轮起为
     收敛评审,只核上一轮问题与修订部分。**修订纪律**:只改被指出的问题,不
     顺带扩写或重写未被指出的章节——每处新增文字都会成为下一轮的评审面,
     也会让收敛轮的"修订部分"变大。minor 可顺手修(只限被指出的条目),
     未修的 minor 由实现阶段经 `__minors` 汇总交接,不必在 plan 阶段修完。
   - **评审运行期间不得修改 plan.md**:脚本在评审结束后核对 plan.md 与本轮
     快照,不一致则本轮作废(exit 3,stderr 含"评审期间被修改",不消耗轮次),
     改完后重跑即可。
   - pass(仅 minor / 无问题)→ 继续。
   拿不准是否采纳某条意见时,不"解释掉"后静默忽略,原样呈用户定夺。
   轮次上限仅当**用户明确要求放宽**时,才在 plan.md frontmatter 写
   `plan_review_max_rounds: <正整数>` 覆盖默认值,并在第 7 步摘要中声明;
   不得未经用户提出而自行写入或建议性写入该字段。
7. 向用户呈现摘要:目标、改动范围、测试用例清单、主要风险;若跑过 plan 评审,
   附评审结论、所用轮次与「范围核对」节的条目(原样转述,交用户裁决)。
   摘要**必带「范围自省」**三问,各一行:① 需求原文要什么、交付是什么;
   ② 改动范围里哪些不是需求直接要求的、为何保留;③ 哪些顺手项已移入
   非目标。不量化,如实自判。明确请求确认。
8. 【确认闸】仅当用户明确表示同意后:将 plan.md 的 status 改为 approved,
   填写 approved_at(日期时间)。用户要求修改则改完回到第 7 步。
9. 在 status 变为 approved 之前,不进行任何源码改动(有 hook 强制)。
